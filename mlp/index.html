Create fit, tune and audit partitions

What we did

Keep identical raw predictor profiles together, then create approximately 70% fitting, 10% tuning and 20% audit data.

Why

Fitting data learns parameters. Tuning data selects model settings and stopping rounds. Audit data reports the frozen choice. These roles prevent us from repeatedly choosing the model on the same data we call a final check.

How it works

hash_pandas_object makes a group identifier from predictors excluding space_id. A 5-fold grouped stratified splitter supplies one 20% audit fold. An 8-fold splitter divides the remaining 80% into 70% fitting and 10% tuning. next(...) takes one split at each level.

Stratification

Try to keep class proportions similar across partitions. It does not require each class to have the same number of rows.

Grouping

Treat rows with the same profile hash as a unit so they cannot cross partitions. This grouping is not operator-disjoint or city-disjoint.

Holdout vs cross-validation

The final notebook uses one grouped holdout arrangement. The splitter class has “KFold” in its name, but these scores are not averages over five fully trained folds.

Data leakage

Information unavailable for honest future prediction influences learning or selection. Even label-free scalers and category vocabularies can leak evaluation information if fitted before the split.

How information is allowed to flow

Initial EDA used the full labelled table. The disjointness boundary here concerns fitted preprocessing, training, early stopping and winner selection; it does not mean no one ever saw audit rows in the exploratory plots.

Split before learning preprocessing¶

A grouped, stratified split assigns about 70% to fitting, 10% to tuning and 20% to a final audit. Model settings and stopping rounds use only the tuning partition. The audit partition is evaluated after settings are frozen. These are random profile splits, so they estimate performance on similar listings rather than generalization to unseen operators or cities.

Turn messy columns into usable features

What we did

Fit reusable feature construction on fitting rows, transform each partition consistently, and prepare model-specific input representations.

Why

Facilities are lists, dates are strings, some numbers are invalid and categories are nominal. Each needs a meaningful representation. Learning caps or vocabularies separately on audit data would change the rules after seeing evaluation data.

How it works

M2FeatureBuilder.fit learns 99.5th-percentile term caps and facilities appearing at least 20 times in fitting rows. transform cleans values, creates intervals/flags/ratios and applies frozen rules. ColumnTransformer then median-imputes and scales numeric inputs and one-hot encodes nominal categories for the two baselines.

fit vs transform

fit learns state such as caps, medians and category levels. transform applies that learned state. Fit on fitting rows and only transform tune/audit until final refit.

One-hot vs multi-hot

One-hot represents one nominal category. Multi-hot allows several facility tokens to be present in the same listing.

Sparse matrix

Store mostly the nonzero entries, useful when category encoding creates many zero-valued indicators. 1,165 columns is not 1,165 original raw columns.

Pipeline / ColumnTransformer

Pipeline chains steps in order; ColumnTransformer applies different steps to chosen columns and combines their outputs.

One feature builder, three input paths

Read left to right. The shared builder creates meaningful columns; the branches prepare different representations for each model family. The final LightGBM uses its native categorical branch, not the baseline 1,165-column one-hot matrix.

What we did

Train a linear classifier, Extra Trees, two LightGBM capacities and CatBoost. Record training F1, tuning F1, tuning accuracy and measured fitting time.

Why

The linear baseline tests additive effects; trees can learn interactions. Two motivated LightGBM settings test a capacity/regularization trade-off without an enormous search. A different boosting implementation checks a different way of handling categories.

How it works

record() fits each estimator and records the same metrics. LightGBM gets fit-only category levels and early stopping after 100 non-improving tuning rounds. The custom callback takes argmax over class scores to calculate macro F1. The table is sorted by tune_macro_f1 before any audit results are used.

Parameters vs hyperparameters

Parameters are learned during fitting. num_leaves, learning_rate and regularization strengths are hyperparameters chosen outside that fitting procedure.

Log loss vs macro F1

Boosted models optimize a differentiable classification loss; the notebook evaluates predictions using macro F1. The tuning metric need not be the same function as the training objective.

Boosting

Add trees sequentially to improve the current model’s loss. For classification, “correcting errors” is shorthand for fitting loss-gradient information, not simply copying the misclassified rows.

Early stopping

Check a validation metric during boosting and retain the best iteration when improvement stalls. It is a model-selection mechanism and therefore uses tuning data here.

Evaluate the frozen model and understand mistakes

What we did

Evaluate all recorded models on audit rows, inspect the selected model’s class report and confusion matrix, group errors and estimate permutation importance.

Why

A single average hides which tier is difficult and which types of listings have more errors. The audit checks the frozen decision. Diagnostics explain its limitations; they do not authorize retuning against that audit.

How it works

The code applies the fitted preprocessing to Xa, selects the input representation matching each model, and predicts without refitting. classification_report shows per-class precision/recall/F1. The confusion matrix normalizes true-label rows. A 2,500-row audit sample and two shuffles per feature support the permutation diagnostic.

Precision

Of the rows predicted as a tier, how many truly belong to it? False positives lower precision.

Recall

Of the rows truly belonging to a tier, how many did we find? False negatives lower recall.

Macro F1

Calculate F1 for each of the four tiers, then average the four values equally. This is not F1 calculated from the macro-average precision and recall.

Permutation importance

Shuffle one feature in a fixed evaluation sample and measure the drop in a fixed model’s score. It measures reliance in that setting, not causality or guaranteed future usefulness.

Refit on all labels and produce the submission

What we did

Relearn preprocessing on all labelled rows, train the already chosen model using its frozen boosting-round count, and produce predictions in sample-submission order.

Why

After honest selection, using all available labels can support the final model. We preserve the selection procedure rather than using the audit again to find a new stopping point. Output alignment matters because correct predictions in the wrong rows are still a wrong submission.

How it works

A new M2FeatureBuilder fits X. The LightGBM branch copies the selected hyperparameters and replaces n_estimators with best_iteration_ (1,508). final.fit then uses all 279,746 labels. The copied sample template supplies IDs; assertions check ID/order, row count, valid tiers and missing values.

Refit

Train a fresh estimator using the frozen recipe on all labelled data. The final estimator is not the exact fitted object previously measured on audit.

Frozen rounds

The 1,508 boosting iterations come from tuning-stage early stopping. Final refitting uses that fixed count without a new audit-based stopping decision.

Hidden test score

The local tune/audit metrics describe labelled partitions. The public leaderboard score describes a different hidden subset and is not guaranteed to equal them.

Submission integrity

Check schema, IDs, ordering, class values and missing entries. These checks establish formatting consistency; they do not prove hidden-label accuracy.

Decision tree

Tree depth vs leaf count

Depth counts decisions along a path; leaves count terminal regions. num_leaves=63 is a capacity limit per tree, not 63 models or depth 63.

Extra Trees

An ensemble of randomized decision trees. It randomizes split candidates more strongly than a conventional random forest. Our setting uses 80 trees, depth at most 20, and at least 5 samples per leaf.

Bagging vs boosting

Independent randomized estimators combine their predictions; boosting builds additions sequentially to improve the current loss. Extra Trees is in the first broad ensemble family but does not bootstrap by default here.

Gradient boosting

Fit successive trees to loss-gradient information and add their contributions with a learning-rate scale. For this classification model, the loss is multiclass log loss.

Precision / recall

Question 10 · related cell ↑

Why median imputation and a missingness flag?

The median provides a simple fitting-set value and is less sensitive to extremes than the mean. A flag lets the model distinguish originally missing values from genuinely observed values near the median. Native boosting branches use their own missing handling.

Question 11 · related cell ↑

What does the facilities parser do?

It safely tries JSON and literal parsing, accepts lists of simple values, strips tokens and removes repeated entries. Malformed values get an explicit flag. Fitting selects sufficiently frequent tokens; transforming uses that frozen multi-hot layout.

Question 12 · related cell ↑

Why use log1p instead of log?

log1p is defined at zero and compresses heavy positive tails. For signed time intervals, sign(days) × log1p(abs(days)) preserves the direction of the interval. I do not claim it makes all distributions Gaussian.

Question 13 · related cell ↑

What happens to a brand-new category at inference?

The baseline OneHotEncoder handles unknown values without learning new columns. The LightGBM frame uses the already fitted category levels, so an unseen value becomes missing. CatBoost receives native strings. I do not fit a new vocabulary on test rows.

Did you scale Extra Trees?

Question 15 · related cell ↑

Why keep separate input representations for models?

The linear baseline needs numeric encoded inputs; sparse one-hot features suit it. LightGBM can consume fitted categorical columns, and CatBoost can use categorical strings. Fair comparison means the same split and metric, not necessarily identical internal representations.

Question 16 · related cell ↑

How does SGDClassifier differ from gradient boosting?

SGD updates coefficients of a linear classifier using stochastic optimization. Boosting builds an additive collection of trees. Both can optimize classification losses, but they represent different kinds of patterns and learn them differently.

Question 17 · related cell ↑

Why is the linear model a useful baseline?

It is fast and tests what an additive model can capture with our representation. It reached tuning macro F1 0.629179. The stronger tree-based results suggest useful nonlinear interactions, but the comparison alone does not isolate exactly which interactions matter.

Question 18 · related cell ↑

How are Extra Trees and a random forest different?

Both combine randomized trees. Extra Trees uses more randomized split thresholds; a standard random forest searches candidate thresholds more directly and commonly uses bootstrap samples. Our Extra Trees configuration uses its default bootstrap=False.

Question 19 · related cell ↑

Explain boosting without saying it just memorizes wrong rows.

At each round it computes information about how the current predictions affect the training loss, fits a tree contribution to improve that loss, and adds a learning-rate-scaled update. For multiclass classification, this is more precise than saying it fits ordinary residual labels.

What do 63 leaves and 1,508 iterations mean?

63 limits terminal regions per tree; it is a capacity setting. 1,508 is the best boosting round found on tuning data. Multiclass LightGBM generally builds a tree for each class per round, so iterations and individual-tree counts are different.

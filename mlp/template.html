What is this project about?

You have a table of workspace listings: capacity, facilities, location codes, operator attributes, reviews, dates and other supplied fields. You want to assign each listing to price tier 1, 2, 3 or 4. You compare several classification methods and submit a predicted tier for each unlabelled test row.

The final selected model is LightGBM with 63 leaves, trained on Kaggle CPU. Here “MLP” names the course, Machine Learning Practice. The selected estimator is a gradient-boosted tree model.

“I built a multiclass classifier for workspace price tiers. I grouped repeated predictor profiles before validation, fitted reusable preprocessing on fitting rows, compared linear and tree-based models, selected LightGBM using tuning macro F1, evaluated the frozen choice, and refitted it on all labels for the final code submission.”

What the project establishes—and its limits

The result we have

Five configurations compared on a fixed fit/tune split. The tuning-selected 63-leaf LightGBM was reported on audit, then refitted on all labels. The actual registered version-3 code submission received 0.70158.

The boundary to describe accurately

Exact-profile groups do not cross partitions. Operators and metros were not explicitly made disjoint. Initial EDA used the full labelled table; later fitted preprocessing, stopping and selection followed the fit/tune/audit roles.

What needs further study

Tier 3 has weaker recall. A group error table or importance plot does not establish why. Operator-disjoint validation and a new development protocol would help test robustness without tuning against the old audit.

Keep the final notebook separate from milestone studies

The final notebook selects one LightGBM model. The M3 L1-selected 200-input classifier and M4 voting/stacking study are separate experiments with different samples and evaluation protocols. Their scores and preprocessing choices must not be presented as if they ran in the final notebook.
